# IC-2 — Observation (engine → agent)

**Schema:** [`observation/v1`](../../spec/schemas/observation.v1.schema.json)
**Status:** FROZEN v1 (founder sign-off 2026-07-26, DECISIONS.md #7). Changes now follow the VERSIONING.md migration procedure with written impact assessment.
**Complete field reference:** [`field-reference.md`](field-reference.md) — generated from the schema descriptions (`spec/tools/gen_field_reference.py`), CI-gated for 100% description coverage, render currency, and reverse-drift (SCH-2). This doc is the curated narrative; the generated reference is the exhaustive one.

## Purpose

One JSON object per decision turn: everything the agent may legitimately know, and nothing else. This is the **only anonymized surface** in the system (ISO-3/ISO-4). The object is JCS-canonicalized, SHA-256-hashed (`ObservationEmitted.observation_sha256`), and stored **in full** at `observations/NNNN.json` in the bundle — SCH-5's "answerable from stored data alone" makes storage non-negotiable; re-derivability via replay is a check, not a substitute.

No `ext` extension point exists on this schema: **the isolation surface is deliberately closed** — any extension slot could carry dates or scenario names.

## Time rebasing (the ISO-4 resolution)

All observation timestamps (`clock_ts`, bar `ts`/`available_at`, funding `ts`, `next_settlement_ts`) are:

```
rebased = real_epoch_ms − time_rebase_offset_ms
time_rebase_offset_ms = largest whole multiple of 604800000 (one week) ≤ pack window.start_ts
```

- **Preserves** time-of-day (funding still settles at rebased 00/08/16 — MATH-4 reasoning intact) and weekday (weekend behavior is a legitimate signal), because one week is a multiple of one day.
- **Destroys** the calendar date: rebased values are < 10^11; real epoch-ms are ~1.7×10^12.
- The offset is recorded in `bundle_manifest.time_rebase_offset_ms` — auditors can map back exactly; the agent container never sees it (ISO-3).
- This deliberately refines the dev-plan sentence "all timestamps UTC epoch-ms": observation times remain epoch-ms *shaped* integers with the same arithmetic, but raw values would make ISO-4 unpassable. All pack/bundle artifacts keep real time.

## CI observation scan (ISO-4, mechanical)

Over every emitted observation: (1) **rebased-timestamp magnitude check, scoped to exactly the five timestamp-shaped fields** — `clock_ts`, `bars[].ts`, `bars[].available_at`, `funding.next_settlement_ts`, `funding.prints[].ts` — none may exceed 99999999999 (an un-rebased epoch leaks as ~1.7×10^12; the schema `maximum` already enforces this, so the scan is a belt-and-suspenders redundancy on emitted instances). The check is deliberately **not** applied to arbitrary integer fields: legitimate money/volume magnitudes exceed 10^11 routinely (e.g. `v_base_1e8` ≈ 1.2×10^12 in the canonical example), so a blanket scan would false-positive on valid data and detect nothing; (2) no string field matches date regexes (`\d{4}-\d{2}-\d{2}`, month names) or the event-name denylist built from all pack `pack_id`/`regime_description` vocabulary (covid, ftx, luna, etf, election, …); (3) `episode_id` matches `^ep_[0-9a-f]{16}$`; (4) property test — **the load-bearing ISO-1 check**: max(`available_at`) ≤ `clock_ts` (rebasing-invariant), cross-checked against pack bytes; the C0.4 poison-row fixture must never appear. For surfaces without an in-band `available_at` (funding `prints[]` carry `ts` only; `last_mark_px_ticks`/`last_index_px_ticks` are derived scalars), the cross-check maps each surfaced value back to its source pack row (provenance mapping) and asserts that row's stored `available_at` ≤ the un-rebased clock — value-equality sentinel scanning alone does not cover them (see the leakage-probe fixture README). **The provenance obligation extends past the literal scalars to every mark-derived value (M0 audit round 2):** `position.<alias>.upnl_micro`, `position.<alias>.dist_to_liq_1e8`, and `account.nav_micro` (NAV includes uPnL) are functions of the current mark price, carry no `available_at`, and can never trip the sentinel scan (a leaked uPnL computed off a future mark is an ordinary large integer, never a sentinel literal). They are discharged by the **single-mark invariant**: the engine MUST compute every mark-derived observation scalar from the SAME mark row whose close populates `last_mark_px_ticks` (and every index-derived value from the row behind `last_index_px_ticks`), so the one provenance check on those scalars covers all of them; CI asserts the invariant arithmetically (recompute uPnL = qty × (last_mark − entry) from in-band fields and require exact equality, floor/ceil per the pinned rounding) and an [ADV] extraction case solves `mark = entry + upnl·1e8/(qty·tick)` on a known position and requires the solved mark to be an `available_at`-legal row.

## Lookback resolution

`effective = run_config value if non-null, else pack default_lookback`, field-by-field (`lookback_bars`, `funding_prints`; V1 defaults 64 / 6). Run config wins — the operator pays the token bill; the pack default is the calibrated recommendation. The effective source is reproducible because `bundle_manifest.run_config` is recorded. **One bar series only**, at the decision interval (no 4h+1h co-mingling — token economy; multi-resolution is a reserved additive field for v2).

## Design decisions (synthesis resolutions)

1. **Week-aligned rebasing** (commerce draft) over episode-relative offsets (trader) or pure relative ages (determinism). Rationale: relative ages are strongest against leakage but scramble time-of-day, breaking natural funding-clock reasoning; window-start-relative offsets scramble weekday/time-of-day unless start is midnight-aligned; week-alignment keeps both while destroying the date. The determinism draft's schema-level guard survives as `maximum: 99999999999` on every rebased field — a raw epoch value is *schema-invalid*, not just scan-caught.
2. **Constraint-mandate risk block** (commerce draft) over flat risk fields (trader/determinism): same facts, but each limit is a typed row with a stable `constraint_id` that `RiskCheck` verdicts reference — the mandate→verdict→conformance triple for Phase-3 commerce (DECISIONS #5). **Extensibility scope, corrected at the M0 audit:** the zero-schema-change claim holds only for *scalar-budget* mandates (`spend_cap` = new `type` row, minor vocabulary bump; per-merchant sub-budgets via the free-string `scope`). *Set/equality* mandates (merchant allowlist, category, currency) cannot ride in an integer `limit`/`used` row: they need an optional value-set field on the constraint row — still a **minor additive** bump under the versioning policy, but a schema change. Decision: no speculative value-set field is reserved in v1 (any concrete shape risks being wrong and the additive path is already cheap); non-scalar mandates are out of scope for `observation/v1` as shipped. Note also that the triple never covered the purchase-decision leg — that leg rides IC-3's `intent_kind` seam (applied at M0 audit round 2): a future `purchase_intent` is a planned **minor** bump, not an `action/v2` major (see IC-3 design decision 6).
3. **No full mark/index bar series in V1** (determinism + commerce majority) vs the trader draft's three series. Compromise: `last_mark_px_ticks` + `last_index_px_ticks` scalars per market expose mark/trade divergence and the funding-notional price cheaply; full engine-side mark/index data remains in the bundle for auditors. Adding series later is an additive minor bump.
4. **Funding schedule observable** (`interval_ms`, `next_settlement_ts`, cap/floor): a real trader knows the venue's funding clock and cap; agents should not reverse-engineer it (resolves open Q16).
5. **`response_deadline_ms` disclosed** in the episode block (trader draft): timeout evidence is only fair and unambiguous if the deadline was told.
6. **Flat positions appear explicitly** with qty 0 and nulls (explicit-null policy for fixed shapes; absence is ambiguous).
7. Funding prints inside observations carry `ts` only (no redundant `available_at = ts`); the pack keeps both for filter uniformity. **Consequence (documented at the M0 audit; extended at round 2):** the in-band `available_at ≤ clock_ts` property is only directly checkable for `bars[]`. Surfaces WITHOUT an in-band `available_at` fall into two groups, both requiring the provenance mapping step in the CI scan above: (a) values a pack row is surfaced into — funding `prints[]`, `last_mark_px_ticks`, `last_index_px_ticks` (traced row-by-row); and (b) **mark-derived scalars** — `position.<alias>.upnl_micro`, `position.<alias>.dist_to_liq_1e8`, `account.nav_micro` — which are *functions of* the mark and are discharged by the single-mark invariant of scan item 4: they MUST derive from the same provenance-checked row behind `last_mark_px_ticks`, CI-verified by exact arithmetic recomputation plus the [ADV] solve-for-mark extraction case (an agent holding a known position can recover the engine's mark as `entry + upnl·1e8/(qty·tick)`; if the engine ever used a not-yet-available mark, that identity IS a price leak). The leakage-probe sentinel scan covers group (a) only at the specific turns where a poison row would align, and group (b) never (a poisoned-mark uPnL is not a sentinel literal) — it is a tripwire, not a proof.
8. **Era fingerprinting via venue constants (ISO-4 honesty, added at the M0 audit):** the observable venue parameters (funding `cap_1e8`/`floor_1e8`, `taker_fee_rate_1e8`, `tick_size_micro`, `qty_step_base_1e8`, `min_notional_micro`) are era-accurate pack data and deanonymize the era independently of price action — ±300000 funding cap *is* 2020-era Binance. Accepted deliberately: a real trader knows the venue's parameters, and hiding them would break the fill/funding reasoning the benchmark tests. Routed to LABEL-2 alongside price-action era recognition; the memorization caveat must name venue constants as a recognition channel, not only price action. (`leverage_cap_lev_1e4` is the protocol's cap, not a venue fingerprint.)
